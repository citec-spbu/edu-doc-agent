# Тесты API, очереди и worker

Обычный запуск не требует Redis/Docker и не читает настоящий `.env`:

```bash
uv run --no-sync pytest
```

Асинхронные сценарии используют `asyncio.run`, дополнительный pytest-плагин
не нужен. PyYAML для проверки Compose уже установлен через dev-зависимость
pre-commit.

## Известные дефекты PR #29

Регрессии из ревью отмечены `pr_review` и выполняются как обычные обязательные
тесты. На них нет `xfail`: падение завершает pytest с ненулевым кодом и блокирует
обязательную проверку `test` в GitHub Actions.

- [P1: публикация Redis](https://github.com/citec-spbu/edu-doc-agent/pull/29#discussion_r4478019738).
- [P2: deadline и ошибки очереди](https://github.com/citec-spbu/edu-doc-agent/pull/29#discussion_r4478029967).
- [P3: конфликт постановки](https://github.com/citec-spbu/edu-doc-agent/pull/29#discussion_r4478047239).

Регрессия повторного startup проверяет освобождение соединений после каждого
shutdown и выполняется без `xfail`: падение блокирует CI. Проверяется состояние
ресурса; допустимы `close()`/`aclose()` и повторное использование клиента или
новый пул.

Только регрессия закрытия при исключении сохраняет
`xfail(strict=True, raises=AssertionError)` и пока не блокирует CI.
После исправления этого дефекта XPASS ломает прогон: нужно снять отметку.

Защита от повторного запуска сессии проверяется с настоящим Redis: пока первая
задача стоит в очереди, второй запрос той же сессии должен вернуть `409`,
не создавая второй задачи. UUID генерируются обычным способом, коллизия не
подставляется. Это требование из backend-архитектуры; текущая реализация
нарушает его, поэтому тест падает без `xfail` и блокирует CI.

Два конкурентных сценария запускают запросы после общего стартового барьера:
одна сессия должна дать `202` и `409` и одну задачу в Redis, разные сессии —
два `202` и две задачи с разными `run_id`. Worker в этих сценариях не запущен,
поэтому задача не может завершиться между запросами. Проверяются также
содержимое очереди и соответствие идентификаторов принятым ответам.

Для текущей реализации при полном запуске всех групп ожидаются **57 passed,
3 failed, 1 xfailed**, без пропусков. Два обычных падения относятся к защите
одной сессии от повторного запуска (последовательные и конкурентные запросы):
API возвращает два `202` вместо `202` и `409`. Третье — к незакрытым соединениям
после второго shutdown. Единственный `xfail` — закрытие при исключении.
Это описание известных дефектов, а не разрешение игнорировать остальные
падения или менять ожидаемые ответы тестов. После исправлений backend
обновить этот результат и снять ставшие `XPASS` отметки.

До снятия `xfail` с повторного startup полный прогон 2026-11-07 на ревизии
`cb418e7` с незакоммиченными тестами и `--run-integration --run-compose`
дал **57 passed, 2 failed, 2 xfailed**.
По JUnit-отчёту совпали точные имена двух падений и двух `xfail`, неожиданных
ошибок и пропусков нет. Покрыты все 90 добавленных исполняемых строк и 6 исходов
ветвлений Python-кода backend относительно `main`; это метрика исполнения,
она не отменяет перечисленные дефекты поведения.

После снятия отметки выборочный прогон только изменённого теста lifespan
дал **1 failed** на проверке освобождения соединений. Новый итог
полного набора выше учитывает изменение классификации одного результата;
весь набор после снятия отметки повторно не запускался.

Контракт тестов: конфликт создания задания → `409`; timeout и ошибки семейства
RedisError → `503`; непредвиденная внутренняя ошибка → `500`. В ошибочном ответе
есть только текстовый `detail`, без внутренних подробностей исключения и статуса
`queued`. Ошибки Redis и внутренние ошибки логируются на уровне ERROR с ID сессии.

Тест молчащего Redis проверяет передачу продуктового deadline **2.0 секунды**,
но запускает короткий таймер только внутри модуля роутера. Внешний watchdog
имеет запас; таймеры самого теста и HTTP-клиента не подменяются. Проверяется
отмена ожидания Redis и отсутствие автоматической повторной постановки при
неизвестном результате записи. Отдельный тест проверяет внешнюю отмену запроса:
она распространяется в очередь и не превращается в HTTP-ошибку.

Для отдельного запуска обязательных проверок ревью (нужен тестовый Redis):

```bash
TEST_REDIS_URL=redis://127.0.0.1:6379/15 \
  uv run --no-sync pytest -m pr_review --run-integration -ra
```

Падение регрессий ревью блокирует CI. Для воспроизведения дополнительных
известных падений lifespan без xfail:

```bash
uv run --no-sync pytest tests/unit --runxfail
```

## Настоящие Redis и ARQ

Явно указать адрес отдельного тестового Redis:

```bash
TEST_REDIS_URL=redis://127.0.0.1:6379/15 \
  uv run --no-sync pytest tests/integration/test_queue.py --run-integration
```

Без адреса тесты пропускаются; при указанном, но недоступном Redis — падают.
Каждый сценарий использует уникальную очередь. Очистка удаляет только собственную
очередь, heartbeat и ключи известных тестовых run ID; FLUSHDB/FLUSHALL не используются.
Worker запускается в burst-режиме с конфигурацией приложения. Трёхсекундная
пауза заглушки подменяется только в модуле задачи, без изменения polling ARQ.
Отдельный локальный smoke запускает настоящие процессы Uvicorn и ARQ CLI,
делает localhost HTTP-запрос и дожидается результата реальной задачи. Его
временные модули задают только уникальное имя очереди; production-код не меняется.

В том же файле есть два fault-сценария с собственным временным контейнером
Redis: остановка и приостановка после успешного запроса. Оба проверяют `503`
при отказе и `202` после восстановления через тот же пул API. Эти тесты требуют
Docker daemon и заранее доступного образа `redis:7-alpine`; образы не скачиваются.
Чужой Redis из `TEST_REDIS_URL` не останавливается. Контейнер использует
случайный localhost-порт, persistence отключён, удаление выполняется в `finally`.
Для запуска только этих двух сценариев внешний Redis не нужен:

```bash
uv run --no-sync pytest tests/integration/test_queue.py --run-integration \
  -k redis_recovers_after_outage
```

## Контейнерный smoke

Заранее собрать образ приложения и подготовить образы БД/Redis:

```bash
docker build -t edu-doc-agent:tests .
docker pull pgvector/pgvector:pg17
docker pull redis:7-alpine
TEST_APP_IMAGE=edu-doc-agent:tests \
  uv run --no-sync pytest tests/integration/test_compose_smoke.py --run-compose
```

Тест не строит и не скачивает образы. Он создаёт отдельный Compose-проект на
основе [основной конфигурации](../compose.yaml): синтетические настройки,
временное хранилище, отдельные тома и случайные localhost-порты API/UI.
Настоящий `.env` не подключается. Публикация портов БД/Redis убрана в тестовой
конфигурации; безопасность исходной публикации проверяется отдельно в unit-тесте.
Проверяются health, Swagger, UI, HTTP → ARQ → результат и логи worker.
В `finally` удаляются только контейнеры и тома уникального тестового проекта.

## Локальная инструкция запуска

[Инструкция в README](../README.md#быстрый-старт) обновлена: локальные API и
worker подключаются к `redis://127.0.0.1:6379/0`, а дополнение Compose через
stdin публикует Redis только на loopback-интерфейсе. В основной конфигурации
порт Redis не опубликован. Ручная приёмка инструкции на отдельном тестовом
окружении:

1. Задать localhost-адрес в `REDIS_URL` и поднять `db redis` командой с дополнением
   Compose из README; дождаться готовности сервисов.
2. Запустить `make run-api`, `make run-worker` и `make run-ui` в отдельных терминалах.
3. Отправить POST `/api/v1/sessions/local-synthetic/process`; получить `202 queued`.
4. Убедиться, что worker завершил задачу с тем же `run_id`, UI и `/docs` доступны.
5. Проверить, что при отсутствии Redis startup API завершается с ошибкой.

При завершении остановить локальные процессы и выполнить `docker compose stop db redis`.
Полный контейнерный запуск использует адрес `redis://redis:6379/0` внутри сети
Compose. Автоматические локальный и Compose smoke проверяют связку процессов;
они не заменяют ручной прогон команд README буквально.

## CI

В [workflow CI](../.github/workflows/ci.yml) выполняются обе группы проверок:

- Job `unit-integration` поднимает PostgreSQL и Redis как service containers, задаёт
  `TEST_REDIS_URL` и запускает unit- и Redis-интеграционные тесты с
  `--run-integration` и покрытием ветвей. Compose smoke в этом job пропускается.
- Job `docker-build` собирает один образ `edu-doc-agent:ci` из текущего checkout
  и загружает его в Docker runner через `load: true`. Затем скачивает готовые
  образы PostgreSQL/Redis и запускает Compose smoke с `--run-compose` и
  `TEST_APP_IMAGE=edu-doc-agent:ci`. Образ используется для API, worker и UI.
- Итоговый job `test` зависит от `unit-integration` и `docker-build` и выполняется
  с `if: always()`. Он успешен только при результате `success` у обоих jobs;
  ошибка, отмена или пропуск любого из них приводят к ошибке итоговой проверки.

Сборка образа и smoke выполняются в одном job. Публикация образа в registry
не требуется. Активный GitHub ruleset
[protect-main](https://github.com/citec-spbu/edu-doc-agent/rules/24883623)
требует проверки `lint` и `test` от GitHub Actions. Сохранено имя обязательного
status check `test`: менять правила репозитория для этой схемы не требуется.
Блокировка заработает для PR после публикации этих изменений и запуска CI.
Исключения `xfail` в остальных тестах не отключаются глобально.

Локальный `make test` сохраняет быстрый режим по составу проверок:
Redis-интеграция и Compose smoke запускаются только с явными флагами и
настройками, приведёнными выше. Обязательные unit-регрессии ревью выполняются
и локально, и в CI.
